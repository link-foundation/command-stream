## Findings, root causes and fixes

### F1: every JS release on main fails with `spawn deno ENOENT` (error)

- **Root cause.** Changesets 3 formats the changelog through `@changesets/format`. With `format` unset, it picks a formatter from the files it finds, and the presence of `deno.json` selects Deno. The release runner has no Deno, so `changeset version` exits 1. This happens after it has already rewritten `CHANGELOG.md` and `package.json`.
  - The template's earlier fix (`devEngines.packageManager: npm`, js-template#154) only changes package-manager detection, not formatter detection.
  - Reproduced at `1fc9e3a` and in the template at `1e43fdb` (`deno on PATH: none`, `config.format = (unset: auto)`).
- **Why no PR check caught it.** `changeset version` ran only in the release job on main. False negative: PR #214 passed every check and then broke every release.
- **Options considered:**
  - install Deno in the release job;
  - delete `deno.json` (it is used by the Deno compatibility tests);
  - pin the formatter.
- **Fix:**
  - `js/.changeset/config.json` sets `"format": "prettier"`. Prettier is already a dev dependency and already formats the changelog in CI.
  - `1d5e33e` runs the release versioning script in the lint job after the fresh-merge simulation and discards its output, so a broken versioning step now fails the pull request.
  - A workflow-hygiene test keeps that step wired.
- **Upstream.** [js-template#214](https://github.com/link-foundation/js-ai-driven-development-pipeline-template/issues/214), with reproduction, workaround and fix; changesets/format#45 tracks the auto-detection.

### F2: signal tests fail under load (flaky false failure)

- **Root cause.** The graceful tests signalled the child after a fixed 300 ms and checked the handler marker after another fixed wait, using the default 100 ms `killGrace` before SIGKILL escalation. On a loaded runner two things go wrong:
  - the shell can still be starting when the signal arrives, so its `trap` is not yet installed;
  - the handler can take longer than 100 ms to run, so the escalation kills it first.
- **Reproduction:**
  - `experiments/issue-216/signal-handler-latency.mjs`, with readiness awaited, measured handler latency after `kill()` at p50 78 ms, p90 158 ms and max 565 ms. At the default 100 ms grace, 12 of 60 handlers never ran; at 5000 ms, 0 of 60 were missing (`validation/signal-latency-ready.log`).
  - Under 96 busy loops on 6 cores, the graceful tests failed 5 of 20 runs before the change and 0 of 20 after. The full signal suite then failed 0 of 15 runs (`validation/signal-before-after.log`).
- **Fix (`472b5d2`).** Each child prints `ready` after installing its traps, and the test waits for it. The handler tests use the 2000 ms grace the Rust suite already used. Markers and heartbeats are polled with a bounded wait (`waitFor`, 5 s) instead of fixed sleeps.
- **Rust (`f154d6d`).** No Rust signal failure was seen in CI, and the old Rust suite did not fail locally under the same load (0 of 15 runs before and after, `validation/rust-signals-before-after.log`). The same readiness-and-polling pattern was applied to keep the two suites in parity. This removes a race; it does not fix an observed failure.

### F3: passing JS jobs print `FAIL bunshell/deno-broken-pipe-*` (false-positive log noise)

- **Cause.** `runCorpus` printed its report to the console, including from unit tests that feed it a reference meant to fail. Scanning a green log for `FAIL` therefore found three lines.
- **Fix (`b5caa65`).** `runCorpus` takes an optional log sink, defaulting to `console.log`, so the conformance runners are unchanged. The tests capture the report and assert on it.

### F4: dependency freshness logs a Cargo warning on every run (false-positive warning)

- **Cause.** `cargo update --dry-run` always prints `warning: not updating lockfile due to dry run`.
- **Fix (`207f913`).** Run a real `cargo update` in a throwaway worktree and fail if `git diff` shows lockfile changes.
- **Verification (`validation/cargo-lockfile-freshness.log`).** It passes on the committed lockfiles and fails with the diff when `itoa` is pinned back to 1.0.15.

### F5: a JS version can reach npm without a GitHub release, and nothing repairs it (false negative)

- **Cause.** `check-release-needed.mjs` returned `should_release=false` whenever npm already had the version. If anything stopped the run between a successful npm publish and `Create JavaScript GitHub Release`, `js-v<version>` stayed missing for good. For 1.0.0–1.4.0 the trigger was the falsely failing publish step fixed in issue 209.
  - npm has 0.9.0–0.9.5 and 1.0.0–1.4.0 with no `js-v` release (the API answers 404 for `js-v0.9.0` and `js-v1.0.0`); js-v0.9.6–js-v0.24.1 and js-v1.5.0 onward exist.
- **Fix (`f5f2127`, the JS template's `github-release-state` approach).**
  - When npm has the version, look up `js-v<version>`.
  - A definitive 404 means `github_release_missing=true`. The publish path runs again with no bump, which is a no-op for a version npm already has, and the release is created.
  - Any other lookup failure is "unknown" and never triggers a release.
- **Validation.** 3 tests fail before and 6 pass after (`validation/github-release-missing-before-after.log`).
- **Limit.** This repairs the *current* version only. Recreating the historical releases (0.9.0–0.9.5, 1.0.0–1.4.0) is a one-time maintainer action that publishes to the repository, so it is not done from this PR.

### F6: the Rust fragment check accepts fragments the release never reads (false negative)

- **Cause.** `check-changelog-fragment.rs` accepted any `.md` under `rust/changelog.d/` (including subdirectories) or under a root `changelog.d/`. The collectors read only the top level of `rust/changelog.d/`. An invalid `bump:` value silently became the default patch.
- **Fix (`1f494d5`).** Only top-level `rust/changelog.d/*.md` counts. Anything else gets a `::warning file=…` annotation. An invalid bump is an `::error file=…`.
- **Validation (`validation/changelog-fragment-check.log`).** The root, nested and typo cases pass before and fail after; the good case passes in both.

`cargo test --all-features` already runs doc tests, and a separate `cargo test --doc` step ran them again. The step was removed (`fcac1d5`), as in rust-template #185.

### F10: Cargo's own warnings never fail the Rust lint job (false negative)

- **Cause.** `RUSTFLAGS=-D warnings` and `clippy -- -D warnings` deny rustc and clippy warnings only. A manifest warning such as `unused manifest key` is printed and Cargo exits 0 (rust-template #181).
- **Fix (`ab115e3`).** The clippy step runs with `--color never`, tees its output and fails with `::error::Cargo reported warnings that -D warnings does not deny` if any `warning:` line remains. clippy's own failures still fail the step, and nothing is compiled twice.
- **Test.** `js/tests/cargo-warnings-gate.test.mjs` runs the real step against a mock `cargo`.

### F11: git rename detection hides added fragments and moved code (false negatives and a false positive)

- **Cause.** Changelog fragments are mostly identical frontmatter. When a PR deletes a pending fragment and adds a new one, git's default rename detection (and `--find-renames` at 50%) reports the pair as `R`, so `--diff-filter=A` finds no new fragment. The check fails a valid PR.
  - The reverse problem applies to changed-path lists. A file moved out of `src/` shows only its new path, so the code change is not seen.
- **Wrong fix, caught in review.** The obvious fix, `--no-renames`, has its own bug: a byte-identical `git mv` of a pending fragment becomes `A`, so moving an old fragment passes as a new one.
- **Results by option** (`experiments/issue-216/rename-detection-repro.sh`, git 2.43, `validation/rename-detection-repro.log`):

  | Option | replaced (must find new.md) | moved (must find nothing) | code-out (must list src/lib.rs) |
  | --- | --- | --- | --- |
  | default | missed | ok | missed |
  | `--find-renames` | missed | ok | – |
  | `--no-renames` | ok | **false pass** | ok |
  | `--find-renames=100%` (additions) + `--no-renames` (changed paths) | ok | ok | ok |

- **Fix (`4edb764` + `9d8b43d`):**
  - Added-fragment checks use `--find-renames=100%`, in `js/scripts/validate-changeset.mjs` and `rust/scripts/check-changelog-fragment.rs`.
  - Changed-path lists use `--no-renames`, in `rust/scripts/detect-code-changes.rs`, the fragment check's code-change list and `.github/scripts/check-language-parity.sh`.
  - `validate-changeset.mjs` reads both columns of an `R` line for code paths.
- **Validation (`validation/changelog-fragment-check-renames.log`, old = main):**

  | Scenario | main | branch |
  | --- | --- | --- |
  | renamed | 1 | 0 |
  | moved | 1 | 1 |

  The new JS test "moving a pending changeset does not add one" fails against the `--no-renames` version.
- **Upstream.** Every template has some form of this bug:
  - [rust-template#190](https://github.com/link-foundation/rust-ai-driven-development-pipeline-template/issues/190) (default detection);
  - [python-template#100](https://github.com/link-foundation/python-ai-driven-development-pipeline-template/issues/100) (`--find-renames`);
  - [js-template#215](https://github.com/link-foundation/js-ai-driven-development-pipeline-template/issues/215) (`--no-renames`, moved fragment).

### F12: one github.com 503 fails the scheduled link check (flaky false failure)

- **Root cause.** lychee 0.24.2 (used by lychee-action v2.9.0) retries only 429 among rejected status codes: `ErrorKind::should_retry`. A 503 is reported after one request whatever `--max-retries` says.
  - `experiments/issue-216/lychee-retry-503.py` (a mock server, run with `python3 -I`) saw exactly 1 request for every combination of `--max-retries` and `--retry-wait-time` (`validation/lychee-retry-503.log`).
  - This is the gap discussed in lycheeverse/lychee#2193.
- **Fix (`da76227`):**
  - `lychee.toml` throttles github.com to 2 concurrent requests 1 s apart (the Rust template's setting), loaded explicitly with `--config lychee.toml`.
  - The lychee step no longer fails by itself (`fail: false`).
  - `.github/scripts/recheck-transient-links.mjs` reads the markdown report:
    - It fetches 429, 5xx, TIMEOUT and ERROR links again, up to 4 times with doubling waits starting at 5 s.
    - It fails at once on any other status.
    - A recovered link is printed as a `::warning::`.
    - The script fails closed if lychee exited with anything but 0 or 2, including an empty code, or if the report cannot be parsed.
  - 8 tests in `js/tests/recheck-transient-links.test.mjs` run it against a local server, and 2 workflow-hygiene tests pin the wiring.
- **Relation to the templates.** All three templates already re-check transient failures outside lychee (`scripts/recheck-broken-links.mjs` in JS and Rust, `scripts/recheck_broken_links.py` in Python), citing lycheeverse/lychee#2297 for connection resets in the connect phase. Their scripts always exit 0, publish an `all_recovered` output, and feed later web-archive and fail steps. This repository's links workflow has none of those steps. Porting the whole chain was weighed against a single fail-closed step, and the single step was chosen: its exit code is the verdict, so a crashed or skipped re-check cannot turn into a pass. The idea is the same as the templates'; the code is smaller, and it is tested against a local server.
- **Note.** The 404 in the same runs was a real broken link, already fixed by issue 209.

### F13: workflow tests fail on Windows checkouts (false failure introduced by this PR, fixed before merge)

- **Evidence.** At `a17623c`, `Test JavaScript (bun on windows-2025)` failed in run 37586000490 and in three earlier branch runs (`ci-logs/branch/js-*-windows-bun.log.gz`). Three tests failed: "the release job re-runs publishing when only the GitHub release is missing", "zizmor runs with the repository policy at low confidence" and "github.com is throttled by the configuration lychee loads".
- **Root cause.** On Windows, the checkout converts the workflow files and `lychee.toml` to CRLF. The new assertions in `js/tests/workflow-hygiene.test.mjs` and `js/tests/github-release-state.test.mjs` split and match on `\n`. The repository's `.gitattributes` pins line endings only for the zx fixtures.
- **Fix (`a7da368`).** Both files normalise `\r\n` to `\n` after reading, as the JS template's `tests/security-workflow.test.js` and `tests/links-workflow.test.js` already do.
  - `experiments/issue-216/crlf-workflow-tests.sh <commit>` converts the files to CRLF in a throwaway worktree and runs the two test files.
  - At `a17623c` the 3 tests fail. After the fix all pass (`validation/crlf-workflow-tests-{before,after}.log`).

### F14: `child_access` probes on Windows wait 5 s, sometimes more than 10 s, for a process that survived the kill (flaky false failure)

- **Evidence.** `rust/tests/child_access.rs` cancels `bash -c 'sleep …'` and requires each attempt to finish within 10 s. Eight Windows Rust jobs were collected: main at `a171ef3`, PR 204's branch, and this branch (`ci-logs/child-access/`, summary in `SUMMARY.txt`, produced by `experiments/issue-216/child-access-timing.py`):
  - About half of all probes take 5.07–5.27 s; the rest take 0.06–0.16 s.
  - Two jobs failed with `child_handle_can_stop_the_process, attempt 0: cancellation exceeded 10 seconds`: 37583836154 (job 112669859843) and 37584217861 (job 112671191150).
  - The test was unchanged by this PR until the fix. The same 5 s pattern appears on main and on PR 204's branch, so the flake predates this PR.
- **Root cause of the 5 s probes (proven).**
  - On Windows, Tokio wraps child pipes in `Blocking` (`tokio/src/process/windows.rs`), so each read runs on a `spawn_blocking` thread.
  - `taskkill /PID <pid> /T /F` (`rust/src/signal.rs`) can miss a descendant created during the kill, such as the `sleep` that Git Bash is still starting. The surviving process keeps the pipe's write end open.
  - The library returns after its bounded drain (`DEFAULT_EXIT_PUMP_GRACE_MS`). Then `#[tokio::test]` drops its runtime, and dropping a runtime waits for every blocking task, including the read that only ends when `sleep 5` exits.
  - `experiments/issue-216/runtime-drop-waits-for-pipe-read.rs` reproduces the runtime half: a plain drop takes 3.01 s, `shutdown_timeout(100 ms)` takes 0.21 s (`validation/runtime-drop-waits-for-pipe-read.log`).
- **Root cause of the more-than-10 s attempts (not established).** The failing jobs ran without process tracing, so the survivors are unknown.
- **Fix (`e607232`).**
  - The probes run on a current-thread runtime that is shut down with `shutdown_timeout(100 ms)`. The test still asserts the library's own deadline but no longer waits on an orphan's pipe.
  - Debug output: if the deadline is missed again, the panic message lists the processes still running (`Get-CimInstance Win32_Process` on Windows, `ps` on Unix), taken before the cleanup kill. The overrun path was exercised locally by setting the deadline to 0.
- **Remaining library defect (documented, not fixed).** A program whose runtime outlives a cancelled command can still keep an orphaned grandchild and a blocking read. Killing the whole tree reliably needs a Windows Job Object, which needs `unsafe` FFI. `rust/Cargo.toml` sets `unsafe_code = "forbid"`, so that is a design decision for the maintainers rather than a CI fix (see Limits).

### F15: Deno on Windows lost the output of three `node -e` cases once (flaky false failure, diagnostics added)

- **Evidence.** In `Bun Shell conformance`, run 37584217932 (`port on Deno on windows-2025`, job 112670557069, `ci-logs/branch/conformance-37584217932-job-112670557069-deno-windows-FAIL.log.gz`), three cases failed with `stdout … got ""` and the correct exit code, after 3163–3317 ms each:
  - `bunshell/change-env-child-process-env-again`;
  - `bunshell/stacktrace-child-uncaught-error-2to1`;
  - `bunshell/input-pipe-between-processes`.
  - The same cases passed on that target at `ab115e3`, `da76227` and `a17623c`. Earlier conformance failures on main (runs 37358951220, 37254239257) were in different cases.
- **Hypothesis (unconfirmed).** `waitForClose` in `js/src/bun-shell/subprocess.mjs` resolves with the exit status 2 s (`CLOSE_GRACE_MS`) after `exit` if `close` never arrives. Any output not drained by then is lost, and the 3.2 s timings fit a slow Node.js start plus that 2 s grace. The code already has default-off tracing for this (`COMMAND_STREAM_TRACE_SUBPROCESS=1` emits `no 'close' 2000ms after exit` and `slow subprocess in <phase>`), but CI enabled it only for Bun on macOS.
- **Change (`2511329`).** `bun-shell.yml` now sets `COMMAND_STREAM_TRACE_SUBPROCESS=1` on Windows and macOS for all targets. The trace only prints warnings, so the results are unchanged. A recurrence will show whether the grace fired. Changing the grace without that evidence could hide hangs that it exists to bound, so it is left as is.

## Existing components used (instead of new code)

- **Changesets `format` option** (`@changesets/format`, Changesets 3) selects Prettier explicitly. changesets/format#45 discusses the auto-detection.
- **`cargo update`** in a worktree instead of `--dry-run`. Renovate and Dependabot were considered, but they open PRs rather than gating CI.
- **The JS template's `github-release-state`** logic was adapted for F5.
- **Gating Cargo warnings** on a teed log follows the Rust template's `check-cargo-warnings.sh`.
- **zizmor-action's `versions` mapping** was read to establish the pinned zizmor version (F8).
- **CodeQL `paths-ignore`** in a config file, as in both templates.
- **git's own `--find-renames=<n>` and `--no-renames`** instead of parsing paths by hand (F11).
- **lychee per-host configuration** (`[hosts."<host>"] concurrency/request_interval`) and lychee-action's `exit_code` / `output` outputs. lycheeverse/lychee#2193 and #2297 were read, along with the templates' `recheck-broken-links` scripts, before deciding that a re-check step is still needed.
- **Debug output** reuses `js/scripts/debug-print.mjs` and the existing `COMMAND_STREAM_TRACE_SUBPROCESS` instead of adding more flags.
- **CRLF normalisation** follows the JS template's workflow tests (F13).
- **Tokio's `Runtime::shutdown_timeout`** stops the probes waiting on blocking reads instead of a custom executor (F14).

  - The cause of the two child_access attempts that took more than 10 s is unknown. The next overrun prints the surviving processes.

- F15 has occurred once. The 2 s close-grace hypothesis is unconfirmed until a traced run reproduces it.
